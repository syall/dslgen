A backend's output is an *object file*: machine code for one program, full of holes
where it calls things it doesn't define (`calc_add`, `calc_sub`, `calc_print`, the C
runtime's startup code). A **linker** fills those holes from libraries and writes an
executable the operating system can run. Since A6, a deliberately temporary
`link_stub.rs` did that job. (Earlier pages link to that file; it's `link.rs` now.)
A12 replaces it with a real link driver, and fixes the ad hoc build machinery that
supplied its libraries.

## What changed, in one paragraph

Built-ins now have one dependency story for all three kinds: each built-in's symbol
comes from a **link unit** (a static archive plus an explicit list of the native
libraries it needs), and linking is *object + every link unit + their dependencies*,
with no library name written in `link.rs`. To get there, the built-in **manifest**
moved into its own data-only crate (`calc-builtins`); `calc-runtime` became
implementations only and now builds its own FFI link unit; and a new crate,
`calc-runtime-artifacts`, builds `calc-runtime` as a static archive with a **real
Cargo build** instead of a bare `rustc` call. That last change means built-in
implementations may use ordinary crates again, and the IPC built-in's protocol is
now JSON via `serde_json` to prove it. rustc itself reports the archive's system
libraries (no more hand-maintained MSVC list). The link driver checks every
built-in's symbol before linking, uses a documented link order, and shows the exact
command when the linker fails. IPC built-ins got the same treatment for run time:
an IPC implementation is now any program speaking the JSON protocol, in any language,
optionally with a **bundle** of files (a multi-file project) that `calcc build` embeds
in the executable; exactly one command per platform, checked at build time; and
`calcc build` reports exactly what the program needs at run time.

## From object file to executable

Take `{ print(2 * 3 + 4 - 1); 7 }`. `*` and `+` lower to `calc_mul`/`calc_add`
(native Rust, A9), `-` to `calc_sub` (C, A10), `print` to `calc_print` (IPC, A11).
The object file a backend emits *references* all four symbols without defining them,
and defines `main`. To produce an executable, the linker must:

- **Resolve every undefined symbol.** It keeps a set of "symbols still needed" and
  looks each one up in the inputs it was given.
- **Pull in only what's used from archives.** A static library (`.a` on Unix,
  `.lib` on Windows) is an **archive**: a bundle of object files ("members") plus a
  **symbol table** listing which member defines which symbol. The linker copies in a
  member only if it defines a symbol that is currently needed, and that member's own
  references join the "still needed" set.
- **Add the C runtime's startup code.** The OS doesn't call `main` directly; it calls
  an entry point (`_start` on Linux, `mainCRTStartup` on Windows) from the C runtime
  library, which sets up the process and then calls `main`.
- **Add system libraries.** `calc_print` spawns a process and pipes its I/O; on
  Windows the code behind that lives in `kernel32.lib`, `ntdll.lib`, `ws2_32.lib`...
  Nothing links those unless someone names them.

That last point is where `link_stub.rs` went wrong. A normal `rustc`-built program
gets its system libraries named automatically. Our object file comes from Cranelift or
LLVM, not `rustc`, so nothing names them, and someone has to.

## One rule for three kinds: link units

| Kind | Link unit (where the symbol is defined) | Its link dependencies | Run-time dependencies | To swap in your own |
|---|---|---|---|---|
| Native Rust (`add`, `mul`) | the `calc-runtime` archive | **derived**: rustc reports them | none | change the function, or add a Cargo dependency, in `calc-runtime` |
| C-ABI FFI (`sub`) | its **own** archive, named by the manifest (`calc_ffi`) | **declared** in the manifest (`link_deps`) | none (it's static; dynamic linking is roadmap.md C7) | provide a library exporting `calc_sub`, and list what it needs |
| IPC (`print`) | the `calc-runtime` archive (the shim that starts the program), plus the program's **bundle**, embedded by the link driver | derived (same list) | **declared**: one command per platform (`python3` on Unix, `python` on Windows), and a cache directory to unpack the bundle into | change the command and/or the bundle: any program speaking the JSON protocol, in any language (see [below](#ipc-implementations-bigger-than-one-file)) |

Why "derived" for Rust but "declared" for FFI? rustc knows every library a Rust archive
needs, because every crate records its `#[link]` requirements and rustc can report
the total. A prebuilt C archive can't be relied on to say: an ELF `.a` has no field
listing the libraries its code expects, and while MSVC object files *may* carry
default-library directives, nothing guarantees they're complete. Its dependencies can
only be *declared* by whoever brings it. (One consequence: a *prebuilt* Rust static library counts as FFI too, and
two Rust static libraries in one executable would each carry a copy of `std`, so they
clash. "Native Rust" means "compiled into the one runtime archive".)

The manifest is the one place those declarations live, in
[`calc-builtins`](../crates/calc-builtins/src/lib.rs):

```rust
Builtin {
    name: "sub",
    symbol: "calc_sub",
    arity: 2,
    kind: BindingKind::Ffi {
        library: "calc_ffi",
        link_deps: &[],        // e.g. &[LinkDep { name: "m", only_on: Some("unix") }]
    },
},
```

`LinkDep::only_on` is the platform restriction: `"windows"` or `"unix"`, Rust's own
`target_family` names. These are the same fields a `bindings.toml` `[[builtin.impl]]`
block will declare in Part B (roadmap.md B6), so B6 parses into types that already
exist.

## Where the runtime archive comes from

Cargo builds every dependency as an `.rlib`, a Rust-only format no C linker reads.
Since A9, `calc-compiler/build.rs` worked around that by running `rustc
--crate-type=staticlib` on `calc-runtime/src/lib.rs` directly. A bare `rustc` has no
idea where `serde_json` lives, so every built-in implementation had to use `std` only.
That's why A11's protocol was a hand-rolled command-line argument.

A12 runs a **nested Cargo build** instead, from
[`calc-runtime-artifacts/build.rs`](../crates/calc-runtime-artifacts/build.rs):

```text
cargo rustc --manifest-path <calc-runtime>/Cargo.toml --lib --crate-type staticlib
            --release --no-default-features --locked --offline --target <triple>
            --target-dir <OUT_DIR>/runtime-target
            -- --print native-static-libs=<OUT_DIR>/calc_runtime.link-deps
```

What each part is for:

- **`--crate-type staticlib`** turns the same crate into a C-linkable archive, with
  its dependencies (`calc-builtins`, `serde_json`, `std`) inside it.
- **`--print native-static-libs=...`** makes rustc write the list of system
  libraries that archive needs. On this project's Windows machine it reads
  `kernel32.lib ntdll.lib userenv.lib ws2_32.lib dbghelp.lib /defaultlib:libcmt`.
  On x86_64 Linux it's something like `-lgcc_s -lutil -lrt -lpthread -lm -ldl -lc`.
  `link.rs` passes that list verbatim, so the archive and its dependencies can never
  disagree.
- **`--target-dir` inside `OUT_DIR`**: the outer `cargo build` holds a lock on its
  own target directory, so a nested build sharing it would wait forever.
- **`+crt-static` on MSVC** (via `CARGO_ENCODED_RUSTFLAGS`) builds everything against
  the static C runtime. rustc then names that runtime itself (`/defaultlib:libcmt`)
  instead of `link.rs` hardcoding `libcmt.lib`.
- **`--no-default-features`** turns off `calc-runtime`'s `link-natives` feature, so
  the archive only *references* `calc_sub` (and the IPC bundle table, below) and
  doesn't contain them. The FFI library stays its own link unit, in exactly the
  position a user's library would be in.
- The build script also drops `RUSTC_WORKSPACE_WRAPPER` (under `cargo clippy`,
  that would lint the nested build too) and the outer build's own `RUSTFLAGS`, and
  re-runs whenever any file in the nested build's own dependency list
  (`calc_runtime.d`) changes. So nothing names `calc-runtime`'s source files.

### How the crates find each other: Cargo's `links` key

`calc-runtime-artifacts` has to find three things that belong to `calc-runtime`:
- its `Cargo.toml`, to run the nested build;
- the `calc_ffi` archive its build script compiled;
- the IPC bundles' source directories.

It never names a path for any of them. They arrive through a small Cargo mechanism
built for exactly this, the `links` key:

```toml
# crates/calc-runtime/Cargo.toml
[package]
name = "calc-runtime"
links = "calc_runtime"
```

**What `links` declares.** "This package links a native library called
`calc_runtime`." Cargo attaches two rules to that promise:
- The package must have a build script, since that's where native linking happens.
- At most one package in a dependency graph may declare a given `links` name. This
  stops two versions of one `-sys` crate from linking two copies of the same C library
  into one program.

That's the classic use: a `-sys` crate (e.g. `libz-sys`) declares `links = "z"`
and its build script finds or builds zlib.

**What it enables: build-script metadata.** A build script normally talks only to
Cargo, through `cargo:` lines on its stdout (`cargo:rerun-if-changed=...`,
`cargo:rustc-link-lib=...`). A package with `links` can also print `cargo:KEY=VALUE`
with a key of its own choosing. Cargo forwards each one to the build script of every
package that *directly* depends on it, as an environment variable named
`DEP_<LINKS>_<KEY>`: the `links` name and the key, uppercased, `-` turned into `_`.
(Rust 1.77 added the more explicit spelling `cargo::metadata=KEY=VALUE`; this crate
uses the older form, which still works.) Here's both ends of it:

```rust
// crates/calc-runtime/build.rs: the producer
println!("cargo:manifest_dir={}", manifest_dir.display());
println!("cargo:ipc_dir={}", manifest_dir.join("ipc").display());
println!("cargo:link_units_dir={}", link_units.display()); // only with `link-natives`

// crates/calc-runtime-artifacts/build.rs: the consumer
fn dep_metadata(key: &str) -> String {
    let var = format!("DEP_CALC_RUNTIME_{key}");
    env::var(&var).unwrap_or_else(|_| panic!("calc-runtime didn't publish {var}"))
}
let runtime_dir = PathBuf::from(dep_metadata("MANIFEST_DIR"));
```

| `calc-runtime` prints | `calc-runtime-artifacts`' build script reads | Used for |
|---|---|---|
| `cargo:manifest_dir=…` | `DEP_CALC_RUNTIME_MANIFEST_DIR` | `--manifest-path` of the nested build, and re-running when its `Cargo.toml` changes |
| `cargo:link_units_dir=…` | `DEP_CALC_RUNTIME_LINK_UNITS_DIR` | where the link driver looks for FFI archives (`calc_ffi.lib` / `libcalc_ffi.a`) |
| `cargo:ipc_dir=…` | `DEP_CALC_RUNTIME_IPC_DIR` | where `calcc build` reads IPC bundles to pack |

Three details matter here:
- **It only reaches direct dependents.** `calc-compiler` depends on
  `calc-runtime-artifacts`, not on `calc-runtime`, so it never sees these variables.
  That's why `calc-runtime-artifacts`' build script passes them on a second way: as
  `cargo:rustc-env=CALC_LINK_UNITS_DIR=…` and so on, which become compile-time
  environment variables for its *own* library, read with `env!` and exposed as
  `LINK_UNITS_DIR`, `IPC_BUNDLES_DIR` and the rest.
- **It travels along a normal dependency.** `calc-runtime-artifacts` lists
  `calc-runtime` under `[dependencies]` even though its library never calls
  `calc-runtime`'s code. The dependency exists for the metadata.
- **Cargo tracks it.** When a published value changes (say, `calc-runtime` moves),
  Cargo re-runs the consumer's build script, so the paths baked into `calcc` can't
  silently go stale.

Why not just write `../calc-runtime` in `calc-runtime-artifacts`? That's exactly
the coupling A12 removed from `calc-compiler/build.rs`. With `links`, the producer
decides where its files are and says so; the consumer only knows the producer's
`links` name. Moving `calc-runtime`, or later swapping it for a generated runtime
crate in Part B, changes nothing on the consuming side.

One related Cargo feature this project doesn't use (yet): because `links` names the
library, a user can override that package's build script entirely from
`.cargo/config.toml` (a `[target.<triple>.calc_runtime]` table supplying the link
flags and metadata by hand). It's a possible hook for spec.md §7.2's "point a built-in
at my own library" overrides (roadmap.md C2). Here that would also skip compiling
`calc_ffi.c` for the interpreter, so it isn't a drop-in answer.

### The `link-natives` feature: one crate, built two ways

`calc-runtime` is compiled in two different situations, and they need different
answers to "where do the C-side symbols come from?". Two symbols are only *declared*
in its Rust code: `calc_sub` (the FFI built-in) and `calc_ipc_bundles`/
`calc_ipc_bundles_len` (the IPC bundle table `calc_print` reads, [below](#embedding-the-bundle-in-the-executable)).
A Cargo feature, `link-natives`, is the switch. Its `build.rs` sees it as the
environment variable `CARGO_FEATURE_LINK_NATIVES`:

| | `link-natives` on (the default) | `link-natives` off |
|---|---|---|
| Who builds the crate this way | Every ordinary dependent: `calc-ir` (the interpreter), `calcc`, every test harness. | Only `calc-runtime-artifacts`' nested build of the static archive, via `--no-default-features`. |
| `calc_sub` | `build.rs` compiles `native/calc_ffi.c` and links it in, so the interpreter calls the real C function. | Left undefined. In a compiled program the separate `calc_ffi` link unit defines it. |
| `calc_ipc_bundles` | `build.rs` links in `native/no_ipc_bundles.c`, an empty table (the interpreter runs bundles from their source directory and never reads it). | Left undefined. The link driver's generated bundle object defines it, holding the program's real bundles. |
| Also produced | The `calc_ffi` link unit for compiled programs: a second compile against the static C runtime, into `$OUT_DIR/link-units/`, published as `link_units_dir`. | Nothing extra. |
| Published either way | `manifest_dir` and `ipc_dir`. | `manifest_dir` and `ipc_dir`. |

Why the archive needs the feature off: a static library bundles the C libraries its
crate links. With `link-natives` on, the runtime archive would carry its own copy of
`calc_sub`. The pre-link check would reject that as exported twice; without the
check, that copy would silently win over a user's swapped-in FFI library. Two
practical notes:
- **Leave it on everywhere else.** In an ordinary dependent, turning it off leaves
  `calc_sub` and the bundle table undefined, and linking that binary fails.
- **Feature unification can't mix the two.** Cargo turns a feature on for every
  dependent in a build once any one of them asks for it. The nested build is a
  separate `cargo` invocation with its own target directory, so the outer build's
  "on" never reaches it.

Only `calc-compiler` depends on `calc-runtime-artifacts`, so the nested build runs
only where linking happens. `cargo test -p calc-ir`, for example, never triggers it.

## The pre-link check: reading an archive's symbol table

When you swap in your own library, the two mistakes that matter are:

- **missing**: your library doesn't export the symbol (a typo, a C++ mangled name,
  forgetting `extern "C"`);
- **exported twice**: two link units define the same symbol, and which one wins
  depends on link order.

Both show up as raw linker errors, if at all, naming a symbol rather than a built-in.
So `link.rs` checks first, reading each archive's symbol table the way the linker
will. On GNU and MSVC archives, the first member is named `/`, and its contents are:

```text
u32 (big-endian)          number of symbols, N
N × u32 (big-endian)      offset of the member defining each symbol
N NUL-terminated names    the symbol names themselves
```

`archive_symbols` parses exactly that. `check_symbols` then requires every manifest
built-in's symbol to be exported by the link unit its kind names, and by no other.
Replace the `calc_ffi` archive with the runtime archive, for example, and `calcc
build` stops with:

```text
calcc: link failed: symbol `calc_add` (built-in `add`) is also exported by library `calc_ffi` (...\calc_ffi.lib); each built-in must come from exactly one link unit
...
built-in `sub` needs symbol `calc_sub` from library `calc_ffi` (...\calc_ffi.lib), but it isn't exported there
```

macOS/BSD archives use a different table layout (`__.SYMDEF`). The check skips
those and leaves them to the linker, which still reports the error, just less
helpfully. On macOS symbol names also get a leading `_`, which `exports` accepts.

## Link order

`link.rs` always builds the command line in this order:

```text
objects  →  calc-runtime archive  →  FFI archives  →  dependency libraries
```

("Objects" is the program's own object file plus the IPC bundle object described
[below](#ipc-implementations-bigger-than-one-file). Object files are always linked
whole, unlike archive members, so their order among themselves doesn't matter.)

Traditional Unix linkers (GNU `ld` and `gold`, the default on most Linux systems,
including CI) read their inputs **once, left to right**. When they reach an archive, they pull out only members that define a symbol
that's *already* needed; they never go back. So whatever *uses* a symbol must come
before whatever *defines* it:

- the object uses `calc_add`, which the runtime archive defines;
- the runtime archive's interpreter table (`calc_runtime::eval`) uses `calc_sub`,
  which the FFI archive defines;
- everything uses the C library and system libraries, which come last.

Swap the two archives (`object → calc_ffi → calc_runtime`) and a Linux link can
fail with `undefined reference to 'calc_sub'`. That happens as soon as a member
pulled from the runtime archive refers to `calc_sub` (the interpreter table does):
by then the linker has already passed `calc_ffi` and won't look at it again. MSVC's
`link.exe` and LLVM's `lld` remember every archive's symbols and would accept either
order, but one order that works for all of them is simpler. The same interpreter table is why *every* FFI
library the manifest declares is linked, even into a program that never calls it:
whether a member referring to `calc_sub` gets pulled in depends on how rustc split
the crate into members, and an unused archive costs nothing.

On MSVC there's one more ordering rule. `cl.exe` accepts `.lib` files as ordinary
inputs, but options meant for the linker itself (like rustc's `/defaultlib:libcmt`)
must come after `/link`. `link_args` sorts the dependency list into those two groups.

## When the linker still fails

If the pre-link check passes and the linker fails anyway (a broken object file, a
missing system library, a toolchain problem), the error shows the exact command line
and the linker's own output. You can copy the command and rerun it by hand:

```text
calcc: link failed: linker exited with exit code: 2
command: C:\...\cl.exe prog.obj ...\calc_runtime.lib ...\calc_ffi.lib kernel32.lib ntdll.lib ... /nologo /Fe:prog.exe /link /defaultlib:libcmt
<the linker's messages>
```

## Run-time dependencies, reported

Some dependencies can't be linked in: `print` needs a Python interpreter on the
machine that runs the program. `calcc build` walks the program's IR, collects the
built-ins it actually calls, and asks each one `Builtin::runtime_requirements()`,
which names exactly what will be used on that platform, never a list of
alternatives:

```text
wrote prog.exe
note: needs at run time: `python` on PATH (built-in `print`)
note: needs at run time: a writable per-user cache directory (or CALC_BUNDLE_CACHE) to unpack bundle `print` into on first run: 2 files, 1023 bytes (built-in `print`)
```

(That's Windows; on Unix the first line names `python3`.) A program that never calls
`print` gets no notes. The method covers every kind, so a dynamically linked FFI
library (roadmap.md C7) will report itself through the same notes.

## IPC implementations bigger than one file

A11's `print` was one Python file, embedded as a string with `include_str!` and run
with `python -c <text>`. That doesn't scale. A real implementation has several
modules and its own dependencies, and "Python on `PATH`" wouldn't describe what it
needs. A12 generalizes the IPC kind so the rule is the same for every language:

> An IPC implementation is **one program speaking the JSON protocol**, plus
> optionally a **bundle**: a directory of files that program needs.

### The protocol

It's a language-neutral contract, implemented by
[`ipc_runtime.rs`](../crates/calc-runtime/src/ipc_runtime.rs) on the calling side:

```text
calc_print(9.0)  ──stdin──▶  {"args": [9.0]}                                 (read until EOF)
                 ◀─stdout──  {"output": "result = 9.00\n", "result": 9.0}    (then exit 0)
```

- Both messages are UTF-8 JSON. The shim relays `output` to the program's stdout and
  returns `result`. The implementation's stderr is free for its own diagnostics.
- JSON has no infinity or NaN, so a non-finite number travels as a string (`"inf"`,
  `"-inf"`, `"NaN"`). Both Rust's `parse` and Python's `float` read those, so
  `print(1 / 0)` prints `result = inf`.
- A11's tests had to normalize `\r\n` to `\n`. Not any more: the newline travels
  escaped inside a JSON string, so Python's text-mode stdout never rewrites it.

This became possible once the runtime archive was a real Cargo build: the shim uses
`serde_json`, which A11's bare `rustc` build couldn't see.

### The manifest entry

In [`calc-builtins`](../crates/calc-builtins/src/lib.rs), nothing is specific to
Python:

```rust
BindingKind::Ipc {
    commands: &[
        IpcCommand { program: "python3", args: &["{bundle}"], env: PYTHON_ENV,
                     probe: Some(&["--version"]), only_on: Some("unix") },
        IpcCommand { program: "python",  args: &["{bundle}"], env: PYTHON_ENV,
                     probe: Some(&["--version"]), only_on: Some("windows") },
    ],
    bundle: Some("print"),     // the directory calc-runtime/ipc/print/
}
```

- **`{bundle}`** in `program`, `args` or `env` stands for the bundle's directory at
  run time. `print`'s bundle is a two-file project (`__main__.py` and
  `formatting.py`); `python <dir>` runs a directory's `__main__.py` with that
  directory on the import path, so its modules import normally.
- **`env`** covers runtimes that find code through the environment. `print` sets
  `PYTHONDONTWRITEBYTECODE=1`, a real lesson from this session: without it, running
  the bundle from its source directory made Python write `__pycache__/` there, and
  `calcc build` then packed that platform-specific bytecode into every executable.
- **`args` and `env` are per command**, not shared, because they legitimately differ
  by platform (Java's classpath separator is `:` on Unix, `;` on Windows).
- **Two different questions about `{bundle}`.**
  - `runs_from_bundle()` asks whether the *executable itself* is in the bundle, and
    only looks at `program`: `python3 {bundle}` still needs `python3` on `PATH`,
    so it's still reported and still probed.
  - `uses_bundle()` asks whether *anything* in the command refers to the bundle
    (`program`, `args` or `env`), and must be true exactly when the built-in
    declares a bundle. Otherwise `calcc build` stops. A `{bundle}` with no bundle
    would be filled in with an empty path (`{bundle}/helper` becoming `/helper`),
    and a bundle nothing refers to would ship in every executable for nothing.
  - For a program inside the bundle, `calcc build` checks the file exists, then
    still runs its probe if it declares one.

Other languages fit without new fields:

| Implementation | `program` | `args` | `probe` | The bundle holds |
|---|---|---|---|---|
| Python project | `python3` / `python` | `{bundle}` | `--version` | `__main__.py`, its modules, optionally `vendor/` (with `PYTHONPATH={bundle}/vendor`) |
| Node.js | `node` | `{bundle}/index.js` | `--version` | `index.js`, `node_modules/` |
| Java | `java` | `-cp`, `{bundle}/print.jar`, `Main` | `-version` | the jar, dependencies shaded in |
| Native helper (Go, C, Rust, ...) | `{bundle}/print` (`print.exe` on Windows) | none | none: the check is that the file exists | the binary |

Deliberately *not* `calcc`'s job:
- **Building the bundle.** `javac`, `npm ci`, `pip install --target vendor` are the
  implementation author's build step; `calcc` packs the directory as it finds it.
- **Version constraints** beyond what the probe checks. An author who needs Java 17
  writes a probe that fails otherwise.
- **A working directory per command.** Considered and left out: runtimes find their
  own files relative to the script or jar, and changing the working directory would
  break programs that read paths relative to where the user ran them.

### One command per platform, checked at build time

A11 tried `python3`, then `python`, at run time. That worked around a real Windows
problem (`python3` there can be an "app execution alias" that starts, exits 9009, and
runs nothing), but it was a guess: which interpreter runs was decided on whatever
machine the program ended up on, and a broken dependency was skipped instead of
reported. Now the manifest names exactly one command per platform (each platform's
standard name), and
[`runtime_deps.rs`](../crates/calc-compiler/src/runtime_deps.rs) runs its probe during
`calcc build`, as spec.md §7 asks ("unreachable executable ... should surface at
`calcc build` time"). Point the Windows command at `python3` on a machine with the
alias, and the build stops:

```text
calcc: built-in `print` needs `python3` at run time, but `python3 --version` failed on this machine (it exited with exit code: 9009: Python was not found; ...); install it, or change the command in the built-in manifest
```

### Embedding the bundle in the executable

A compiled program carries its bundles *inside* the executable, so there's still
just one file to ship. Every program that needs real files (an interpreter, `java`,
`node`, a helper binary) needs them on disk, though, so embedding means "carry them
in the executable, unpack them on first run", which is what PyInstaller's one-file
mode, Node's `pkg` and Deno/Bun `compile` all do. Here's how:

1. **Pack.** `runtime_deps::prepare` reads each used bundle's directory (sorted, so
   the result doesn't depend on directory order; symlinks followed) and packs them
   into one blob in the format defined in
   [`bundle_format.rs`](../crates/calc-builtins/src/bundle_format.rs): a magic
   string, then per bundle its name, a content hash, and each file's path, Unix mode
   and bytes. One definition, used by both the packing and the unpacking side.
2. **Embed.** The link driver writes one more object file itself, with the
   [`object`](https://crates.io/crates/object) crate: COFF, ELF or Mach-O depending on
   the target, holding the blob in its read-only data section under two symbols,
   `calc_ipc_bundles` and `calc_ipc_bundles_len`. It's the link driver producing an
   object file of its own. A linker resolves a *data* symbol exactly like a function
   symbol: the shim in the runtime archive declares both `extern`, and this object
   defines them. The blob is flat bytes, so the object needs no relocations.
3. **Unpack.** On first use, the shim reads the blob through those symbols and
   unpacks the bundle to `<cache>/calc-bundles/print-<hash>/`, where `<cache>` is
   `%LOCALAPPDATA%` on Windows, `$XDG_CACHE_HOME` or `~/.cache` on Unix, or
   `CALC_BUNDLE_CACHE` if set.
   - **Per-user, not a shared temp directory.** With a predictable path in `/tmp`,
     another user could plant files there first.
   - **Named by content hash**, so a changed bundle never reuses a stale copy, and an
     existing directory is simply reused.
   - **Written to a temporary sibling, then renamed into place**, so two copies of
     the program starting at once can't see a half-written bundle.
   - **Unix file modes restored**, so a bundled helper binary stays executable.

The interpreter doesn't unpack anything: `calcc run --interpret` runs the same shim on
the bundle's source directory. Rust programs that link `calc-runtime` (`calcc`, the
test harnesses) still need `calc_ipc_bundles` to resolve, so `calc-runtime`'s build
script links an empty table into them (`native/no_ipc_bundles.c`), the same way it
already supplies `calc_sub`.

Alternatives considered:
- **Appending the bundle to the end of the executable**, found at run time by reading
  the program's own file. It's simpler (no generated object), but it breaks code
  signing on macOS and Windows. Deno moved away from it for that reason.
- **A directory next to the executable** (`prog.bundle/`). No unpacking, but two
  things to ship and keep together.

## Platforms

`link.rs` uses the system C toolchain as its linker driver, found by the `cc` crate,
in one of two command-line styles:

- **Tested**: x86_64 Windows with MSVC (`cl.exe`), x86_64 Linux with `cc` (CI).
- **Supported by construction, untested**: macOS (Apple clang), Windows with MinGW or
  clang-cl, the BSDs, aarch64 Linux. They take the same two paths, and rustc
  reports the right dependency list for each. On non-x86 hosts only the Cranelift
  backend works for now, because the LLVM backend is built with x86 support only
  (roadmap.md C8 lifts that).
- **Anything else** (a toolchain that's neither MSVC-like nor GNU/Clang-like) is an
  explicit `unsupported toolchain` error.
- **Picking a different linker driver**: set `CC` (or `CC_<target>`), which `cc`
  already honors.
- **The target is always the host for now.** It's chosen in exactly one place
  (`calc_runtime_artifacts::TARGET`), so cross-compilation (roadmap.md C8) only has to
  make that selectable.

## What it costs, and what's deliberately not here

- **A slower first build.** The nested build compiles `calc-runtime` and its
  dependencies a second time, in release mode, the first time `calc-compiler` builds.
  Later builds reuse it.
- **`calcc` still only works inside its build tree.** The archive's path is baked in
  at build time, as it was since A9. Shipping `calcc` elsewhere would need the archive
  embedded or installed next to it. Deferred.
- **Swapping still means rebuilding `calcc`.** The manifest is Rust code for now.
  Overriding a built-in's location without rebuilding is spec.md §7.2 (roadmap.md C2).
- **Embedded bundles make executables bigger**, and the first run pays for
  unpacking. A large `node_modules` makes a large binary.
- **Not here**: dynamic linking of FFI libraries (C7), cross-compilation (C8), a
  `wasm32` target with its own linker, `wasm-ld` (C1-wasm, optional),
  `--verbose`/`--keep-object` flags (the CLI is A13's), and cleaning up old bundle
  versions in the cache.

## Try it

```bash
# bash / zsh / Git Bash
cd calc-lang
cargo build
printf 'print(2 * 3 + 4 - 1);\n7' > prog.calc
./target/debug/calcc build prog.calc -o prog   # wrote prog / two "needs at run time" notes
mkdir -p /tmp/elsewhere && cp prog /tmp/elsewhere/ && cd /tmp/elsewhere
./prog; echo $?                                # result = 9.00 / 7
ls ~/.cache/calc-bundles                       # print-<hash>
```

```powershell
# Windows PowerShell
cd calc-lang
cargo build
Set-Content -Encoding ascii -Path prog.calc -Value "print(2 * 3 + 4 - 1);`n7"
.\target\debug\calcc.exe build prog.calc -o prog
New-Item -ItemType Directory -Force $env:TEMP\elsewhere | Out-Null
Copy-Item prog.exe $env:TEMP\elsewhere\
& $env:TEMP\elsewhere\prog.exe                # result = 9.00
$LASTEXITCODE                                  # 7
Get-ChildItem $env:LOCALAPPDATA\calc-bundles   # print-<hash>
```

One program, all three kinds, run from a directory holding nothing but the
executable: `*` and `+` come from the Cargo-built runtime archive, `-` from the
separate `calc_ffi` archive, and `print`'s two-file Python project comes out of the
executable itself. Try changing `describe` in
`crates/calc-runtime/ipc/print/formatting.py` and rebuilding: the program prints the
new format, and a second `print-<hash>` directory appears in the cache. Or change
`calc_sub` in `crates/calc-runtime/native/calc_ffi.c` to `return a - b + 100;`: the
program prints `result = 109.00`. Neither change touches `calc-compiler`.
